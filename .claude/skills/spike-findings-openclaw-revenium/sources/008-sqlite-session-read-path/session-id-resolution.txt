CANDIDATE 2 — CLI metadata (openclaw sessions list --json, most-recent-interaction)
================================================================================
Mechanism: `openclaw sessions list --json`, sorted client-side by
  lastInteractionAt/updatedAt descending, with cron sessions excluded by key
  (mirroring the existing scripts' `agent:main:cron:*` key-pattern exclusion, adapted to
  whatever key shape 2.0 cron sessions actually use).
Command: openclaw sessions list --agent dev --json, then Python: filter out any session
  whose key's last colon-segment is "cron", sort remaining sessions by
  lastInteractionAt/updatedAt descending, take the first.
Raw output (the selected session):
  {
    "key": "agent:dev:main", "updatedAt": 1790231241323, "ageMs": 117841,
    "sessionId": "c50833a3-3b91-4111-8a79-9dbcd8d294d3",
    "sessionStartedAt": 1790230335400, "lastInteractionAt": 1790231241319,
    ..., "agentId": "dev", ...
  }
VERDICT: CORRECT. sessionId matches ground truth exactly
  (c50833a3-3b91-4111-8a79-9dbcd8d294d3). The surface provides both `lastInteractionAt`
  and `updatedAt` timestamp fields, sufficient for a script to determine recency itself
  regardless of the CLI's own internal default ordering.
CRON-CONCURRENT CHECK: NOT VERIFIED LIVE. This host has no cron-scheduled session
  currently running for either agent (this skill's own cron install is out of scope for
  Phase 17), so there was no real concurrent cron session to test the exclusion filter
  against. The candidate's exclusion LOGIC is sound in principle (skip any session key
  ending in a cron-shaped segment) but this probe could not confirm what 2.0's actual
  cron-session key SHAPE is (the old convention was `agent:main:cron:*`; 2.0's
  `session_nodes.created_via` enum includes a `'cron'` value — see CANDIDATE 3 below —
  which may be a cleaner signal than key-pattern matching for this surface too, but that
  value is not exposed in the `sessions list --json` payload itself). Flagged as an open
  item for Phase 19 to confirm against a real cron-scheduled 2.0 session.
SANDBOX CELL: mechanism reachable, correctness unverifiable this run. Command:

CANDIDATE 3 — Direct SQL (session_nodes, ordered by updated_at, created_via != 'cron')
================================================================================
Mechanism: query the captured schema's session_nodes table (see schema-capture.sql.txt)
  for the most recently updated non-cron session. Only identifiers present in
  schema-capture.sql.txt are used.
Command: sqlite3 -cmd "PRAGMA busy_timeout=5000;" "file:<db>?mode=ro"
  "SELECT session_key, current_session_id, created_via, updated_at FROM session_nodes
   WHERE created_via IS NULL OR created_via != 'cron' ORDER BY updated_at DESC LIMIT 1;"
Raw output: agent:dev:main|c50833a3-3b91-4111-8a79-9dbcd8d294d3||1790231241323
VERDICT: CORRECT. current_session_id matches ground truth exactly. This is the strongest
  candidate found: `session_nodes.created_via` is a first-class, schema-enforced enum
  column (`CHECK (created_via IS NULL OR created_via IN ('operator', 'spawn', 'channel',
  'cron', 'talk', 'run', 'plugin', 'internal'))` — see schema-capture.sql.txt) that
  directly answers "was this session created by cron" without any filename/key-pattern
  parsing at all — a structural improvement over the old *.jsonl-glob-plus-key-exclusion
  approach the four production scripts currently use.
CRON-CONCURRENT CHECK: NOT VERIFIED LIVE, same reason as CANDIDATE 2 — no real
  cron-created session exists on this host to confirm `created_via` actually gets set to
  `'cron'` by an OpenClaw-scheduled (not manually-typed) turn. This probe DID confirm the
  column exists, is schema-enforced, and correctly returns the ground-truth session when
  filtered (trivially, since no cron session exists to filter out yet). Observed
  `created_via` values seen live on this host across both cells:
  `NULL` (agent:dev:main / agent:main:main's original chat-driven sessions),
  `'run'` (the NemoClaw-sandbox session created via `nemoclaw revenium-2-0 agent`, per
  Task 1/2's AUTH_PROFILE_MIGRATION_REQUIRED finding). Confirming `'cron'` is what a real
  OpenClaw-internal cron turn sets is the same open item flagged under CANDIDATE 2, for
  Phase 19.
SANDBOX CELL: mechanism reachable, correctness partially confirmed. Command:
  `sqlite3 -cmd "PRAGMA busy_timeout=5000;" "file:$HOME/nemoclaw-revenium-2-0-mount/agents/main/agent/openclaw-agent.sqlite?mode=ro" "SELECT session_key, current_session_id, created_via, status, updated_at FROM session_nodes WHERE created_via IS NULL OR created_via != 'cron' ORDER BY updated_at DESC LIMIT 5;"`
  Raw output: agent:main:main|92d5ab49-f175-494a-ba5a-f4a595bca303|run|failed|1790229671148
  The query runs cleanly over the SSHFS mount (mode=ro, busy_timeout, zero errors) and
  the schema's `created_via` column is present in this cell too (see schema-capture.sql.txt
  CELL SSHFS) with the SAME enum shape as HOST-LOCAL. `created_via='run'` on this row
  independently confirms Task 1/2's finding that the NemoClaw `agent` subcommand wrapper
  is what created this session shell. No ground-truth CORRECT/INCORRECT verdict is
  possible here (no completed turn exists in this cell to check against), but the
  candidate mechanism itself is confirmed structurally sound on both cells.

CANDIDATE 4 — Hook payload
================================================================================
Mechanism: whether a plugin hook payload carries the session key for the current turn.
Not live-tested in this probe (the full hook-firing matrix, including per-model
behavior, is plan 17-05/SPIKE-02's dedicated job — this task records the candidate
shape only, per the task's own scope).
Documented shape (RESEARCH.md `## Hook Catalog`, confirmed live-docs this session):
  - `subagent_spawned` includes `childSessionKey` (plus `resolvedModel`/`resolvedProvider`
    "when OpenClaw has resolved the child session's native model before launch").
  - `subagent_ended` carries `targetSessionKey`, `targetKind`, `reason`, optional
    `outcome`/error details/timing — but explicitly does NOT include `agentId`;
    correlation across the two hooks runs through the session key
    (`targetSessionKey` <-> `childSessionKey`), not the agent id.
  - Neither hook is documented as firing on the CURRENT (parent/root) session's own
    identity — they carry the CHILD/subagent's session key, which answers "which
    subagent session is this" but not "which session is the CALLING (parent) turn in."
    No hook in the confirmed catalog (`before_prompt_build`, `after_tool_call`,
    `before_agent_finalize`, etc.) is documented as passing the CURRENT session's own
    key/id to a handler in a way a shelled-out script (not a plugin handler) could read.
VERDICT: NOT APPLICABLE as answered by docs alone for a NON-plugin script's own
  "which session am I in" question — the hook payloads that DO carry a session key are
  scoped to subagent relationships, observed from INSIDE a plugin handler (JS/TS code
  registered via `api.on(hookName, handler)`), not accessible to an externally-invoked
  shell script the way `write-marker.sh` is invoked. A plugin COULD write the current
  session key to a file for a script to read afterward (this is architecturally what
  candidate (c), the plugin-hook sidecar, would do), but that is a different mechanism
  than "the hook payload itself tells a shell script its session id," which this
  candidate's phrasing asks about. Recorded as a documented negative finding at the
  docs level; a live hook-payload capture (plan 19/SPIKE-02) could still surface an
  undocumented field this session did not check.
CRON-CONCURRENT CHECK: not applicable — not live-tested.
SANDBOX CELL: not live-tested (same as HOST-LOCAL — this candidate is docs-only in this
  probe; a hook-payload capture requires an installed plugin, which is plan 19/SPIKE-02's
  scope, not this task's).

================================================================================
RECOMMENDATION
================================================================================
RECOMMENDATION: CANDIDATE 3 (direct SQL against session_nodes, ordered by updated_at
  DESC, filtered on created_via != 'cron') is the mechanism Phase 19 should port
  write-marker.sh, write-job-marker.sh, verify-markers.sh, and guardrail-check.sh onto.
  It resolved correctly against live ground truth, uses only schema-verified
  identifiers, requires no CLI-agent-registry dependency (unlike CANDIDATE 2, which
  Task 2's cli-surface-output.txt showed is blind to an unregistered agent id such as
  the ad-hoc "main" store on the standalone HOST-LOCAL cell), and replaces the old
  filename-glob-plus-key-exclusion heuristic with a first-class, schema-enforced
  `created_via` provenance column — a structural improvement, not just a like-for-like
  port. CANDIDATE 2 (CLI metadata) is the fallback if a future build removes CLI access
  to `session_nodes`-equivalent detail, but it inherits the agent-registry gap
  CANDIDATE 3 does not have.
  OPEN ITEM carried to Phase 19: confirm live that `created_via` is actually set to
  `'cron'` by an OpenClaw-internal cron-scheduled turn (not a manually-invoked one) —
  this host had no real cron session to test that specific value against.
