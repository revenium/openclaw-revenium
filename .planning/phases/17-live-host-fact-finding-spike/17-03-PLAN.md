<objective>
Run the first two of SPIKE-01's three read-path candidates against the live 2.0 host, and answer D-03's second determination: how a script on 2.0 resolves "which session am I in right now". Candidate (a) is a direct, read-only, WAL-aware `sqlite3` read of `openclaw-agent.sqlite`, captured as a verbatim schema dump plus literal sample rows; candidate (b) is the real `openclaw sessions` subcommand family plus `doctor session-sqlite inspect`.

Purpose: D-02 ranks candidates on data fidelity first — the winner is whichever mechanism yields per-completion token usage, model id, toolCalls, and session parentage with zero loss, because a mechanism that is fast but silently drops token counts reproduces the exact fail-open blackout this milestone exists to close. RESEARCH established from official docs that no SQL table or column name is published anywhere, that `sessions tail` redacts tool arguments and prompt text by design, that `sessions list --json` carries session-level metadata only, and that `export-trajectory`'s "owner approves the exec request" language leaves unattended invocation unconfirmed. None of that is a substitute for running them. D-03 exists because four production scripts resolve the current session by globbing the newest non-cron `*.jsonl` filename and never read message content at all — answering only the content half would leave them with no fact to port against in Phase 19.
Output: `.planning/spikes/008-sqlite-session-read-path/` populated with two throwaway probes, the verbatim schema capture, literal sample rows, per-surface CLI output, and the session-id resolution answer. The ranking and the written determination land in plan `17-04`.
</objective>
